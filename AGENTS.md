# AGENTS.md

Контекст для агентов/ассистентов, работающих с этим репозиторием. Для
быстрого старта — см. `README.md`. Полная спецификация и план —
`docs/superpowers/specs/2026-08-21-mr-informer-spec.md` и
`docs/superpowers/plans/2026-08-21-mr-informer.md`.

## Что это

Node.js Telegram-бот: раз в `POLL_INTERVAL_MS` (по умолчанию 3 мин) опрашивает
один GitLab-проект (`GITLAB_PROJECT_PATH`), по лейблам MR определяет, чья
сейчас очередь действовать (автор/ревьюер), и шлёт личные Telegram-уведомления
плюс повторные напоминания раз в `REMINDER_INTERVAL_MS` (по умолчанию 30 мин),
пока статус не сменится. Полностью read-only к GitLab — только `GET`.

## GitLab за корпоративным VPN — критично для деплоя

`git.fix-price.ru` фильтрует доступ на уровне edge/WAF (виден как `Angie` в
заголовках ответа). Случайный внешний сервер (VPS, облако) получает
`403 Forbidden` даже на `GET /`, без какой-либо связи с токеном или правами
доступа. Работает только с машины, у которой и так есть доступ к
корпоративной сети — обычно рабочий ноутбук/десктоп сотрудника.

Проверка перед любым деплоем на новую машину:

```bash
curl -I https://git.fix-price.ru
```

`302` на `/users/sign_in` — доступ есть, можно деплоить сюда.
`403 Forbidden` от `Angie` — эта машина не подходит, нужен VPN/другая машина.

Уже ловили это на практике: сначала подняли бота на VPS `62.84.99.53`, он не
крашился (ошибки GitLab API перехватываются штатно в `tick()`), но каждый
цикл поллинга падал в 403 — пришлось переносить на рабочую машину
пользователя.

## Реальные названия лейблов в проекте

Лейблы в GitLab — с заглавной буквы и не всегда дословно совпадают с тем, как
их называют в разговоре. Актуальные строки живут в `src/labelState.js`
(`LABELS`): `Ожидает ревью`, `Ревью`, `Требуются уточнения`, `Готово`.
Сравнение строгое (case-sensitive) — несовпадение молча уводит MR в
состояние `no_label` вместо реального статуса. Уже ловили этот баг в проде
(бот присылал «проставь статус MR» на MR, где лейбл на самом деле стоял).
Если лейблы в GitLab переименуют — нужно синхронно поправить эти константы;
источник истины — сам проект, не то, что написано в спеке/плане.

## Мультиинстансный паттерн (если больше одного человека)

Каждый деплоящий заводит СВОЙ Telegram-бот (свой токен через @BotFather) и
свой `.env` — общий бот/токен между инстансами не работает: Telegram
разрешает только один активный `getUpdates` на токен бота, второй инстанс
будет падать в `TelegramError: 409 Conflict` и рестартовать в цикле (уже
ловили). `ALLOWED_GITLAB_USERS` при этом одинаковый у всех инстансов — по
нему бот решает, какие MR вообще отслеживать. `GITLAB_TOKEN` у каждого
свой, персональный.

## Групповой лог прогресса — не используется сейчас

В коде есть поддержка `GROUP_CHAT_ID` (`src/notifier.js` → `notifyGroup`,
`createNotifier`) — если переменная пуста, `notifyGroup` тихо ничего не
делает, это дефолтное и текущее состояние. Фичу сознательно не разворачиваем
и не документируем в README, пока явно не попросят вернуться к ней. Если
попросят — там же есть нюанс: при нескольких инстансах на одном проекте
заполнять `GROUP_CHAT_ID` можно только в одном из них, иначе лог задвоится.

## Хранилище и состояние

Плоский JSON-файл `data/store.json` (путь настраивается `STORE_PATH`) —
последнее известное состояние по каждому MR, флаг `dmDelivered` (доставлено
ли личное сообщение конкретному человеку — отдельно от каданса напоминаний,
чтобы не спамить группу, пока ответственный не зарегистрирован через
`/start`), и маппинг Telegram `chat_id` ↔ GitLab-логин. Файл перечитывается
с диска на каждый вызов (без кеша в памяти) — конкурентная запись извне не
предусмотрена, не редактировать руками при запущенном боте.

## Деплой на VPS вместо личной машины

Возможен, но только если у самого VPS есть доступ к `git.fix-price.ru` (см.
выше — проверить `curl -I`). Тогда деплоить как обычный systemd-сервис от
системного пользователя (`useradd --system`, `EnvironmentFile=.env`,
`Restart=on-failure`) — по аналогии с systemd `--user` unit из README, но
`system` вместо `user` и отдельный системный пользователь вместо текущего.
