# mr-informer — Spec

Собрано в grill-сессии 2026-08-21, подтверждено пользователем.

## Проблема

Два вайбкодера ревьюят друг друга по циклу: автор ставит лейбл MR
`требуется ревью` → ревьюер берёт в работу, ставит `ревью` → бот-ревьюер
отписывается в MR и лейбл меняется на `требуются уточнения` или `готово` →
если `готово`, ревьюер мержит. Схема рабочая, но есть заметный лаг между
сменой состояния и реакцией нужного человека (не видят, заняты, отвлеклись,
кончились токены и т.д.).

## Источник данных

Поллинг GitLab REST API раз в 3 минуты, read-only персональный токен.
Self-hosted GitLab: `https://git.fix-price.ru/android/fixprice_serbia/`.
Без вебхуков (недостаточно прав на добавление webhook в проекте).

## Область охвата

Один проект, один раз — без мультитенантности. Whitelist по двум конкретным
GitLab-логинам: отслеживаем MR, где автор ИЛИ ревьюер — один из этих двух
логинов. Остальные MR в репозитории игнорируются.

## State machine

Лейблы MR меняются людьми/ботом вручную (не эта система).

| Состояние | Кто действует | Что делает | Напоминание |
|---|---|---|---|
| MR не-драфт, лейбла нет, прошло ≥15 мин с создания | Автор | Проставить статус | каждые ~3ч, рабочее окно |
| `требуется ревью` | Ревьюер | Взять в ревью → `ревью` | каждые ~3ч, рабочее окно |
| `ревью` | — (ждём бота-ревьюера) | без действия человека | нет |
| `требуются уточнения` | Автор | Поправить, вручную вернуть `требуется ревью` | каждые ~3ч, рабочее окно |
| `готово` | Ревьюер (человек) | Замержить | каждые ~3ч, рабочее окно |
| MR draft | — | ничего | нет |

Рабочее окно напоминаний: **9:00–19:00 МСК, Пн–Пт**. Первая нотификация о
новом состоянии/новом MR отправляется сразу, независимо от рабочего окна;
окно ограничивает только повторные напоминания.

## Доставка уведомлений

- **Личка (DM)** — единственный канал actionable-уведомлений, лично
  ответственному человеку.
- **Отдельная Telegram-группа** — лог всех переходов состояний для
  визуального контроля прогресса, без меншенов/адресности (просто текст,
  кто сейчас ответственный).

## Регистрация пользователей

Команда `/start` → бот спрашивает GitLab-логин → пользователь присылает его
текстом → бот сохраняет пару `chat_id ↔ gitlab_username`. Никакой ручной
правки конфига администратором.

## Поведение при первом запуске

При старте сервис сразу сверяет текущее состояние всех отслеживаемых MR и
рассылает уведомления по всем уже "зависшим" action-item — не ждёт первого
нового изменения после запуска. (Технически это следует само собой из того,
что стор начинает пустым: любое текущее action-состояние воспринимается как
новое по сравнению с пустой историей.)

## Хранилище

Плоский JSON-файл на диске: последнее известное состояние по каждому MR,
время последнего напоминания, маппинг `chat_id ↔ gitlab_username`.

## Стек и деплой

Node.js (>=20, ESM, глобальный `fetch`, встроенный `node:test`). Простой
процесс, разворачивается на VPS позже (вероятно systemd). Секреты
(`TELEGRAM_BOT_TOKEN`, `GITLAB_TOKEN`) — через `.env`, не в git.

## Границы

Бот полностью read-only по отношению к GitLab: только читает лейблы/поля
MR через API, ничего не пишет, не меняет лейблы, не оставляет комментарии.
Вся запись — только в Telegram (сообщения) и в локальный JSON-стор.

## Вне скоупа

- Мониторинг длительности состояния `ревью` (насколько долго крутится
  бот-ревьюер).
- Мультипроектность / несколько пар вайбкодеров.
- Автоматизация смены лейблов в GitLab.
- Команды типа `/status` (обсуждались как идея, но не вошли в
  подтверждённый финальный скоуп).
